1 · Overview

What this platform is

A self-service, browser-based lab environment where each student gets their own login, pastes in their own (or a pre-configured shared) API credentials, and chats with Claude — which calls ThousandEyes, Meraki, and (optionally) Splunk through official hosted MCP servers to actually complete tasks, not just describe them.

  • Students never install anything — everything runs in this web app (Flask on EC2), reached over HTTPS.
  • Chat is powered by Claude on AWS Bedrock; login is AWS Cognito (Hosted UI, OAuth).
  • Per-student credentials (ThousandEyes token, Meraki key, Splunk URL) are encrypted and stored in DynamoDB — never in source code.
  • Every chat turn is logged to Galileo for observability (tool selection quality, error rate, instruction adherence, etc.) — optional, but on by default in this deployment.
  • Proctors get a separate admin area (this page, plus Students / Classes / Progress / Settings) gated by an explicit proctor allow-list, not just "any logged-in user."

3 · Architecture

Architecture at a glance

Compute & hosting

  • Single EC2 instance (us-east-1) running Flask under gunicorn, managed by systemd (flask-app.service)
  • Code lives in a git repo (GitHub) — deploys are a git pull + service restart
  • Public URL fronted by HTTPS (Nginx/ALB depending on env) — APP_URL in config

Identity

  • AWS Cognito user pool — students self-register via the join flow; proctors are added manually or via PROCTOR_EMAILS
  • One permanent super admin email, hard-coded (SUPER_ADMIN_EMAIL), can never be removed
  • Session-based login (Flask session cookie) after Cognito Hosted UI OAuth callback

AI & tools

  • Claude (Haiku 4.5 by default) via AWS Bedrock — does the actual reasoning and tool selection
  • MCP servers: ThousandEyes (Cisco-hosted), Meraki (Cisco-hosted), Splunk (optional) — Claude calls these directly with each student's own bearer token
  • Galileo observability — every chat turn logged as a trace with LLM/tool/agent spans and scored on 6 metrics

Data

  • DynamoDB table for per-student encrypted credentials, connection status, and progress checkpoints
  • DynamoDB table for scheduled classes and their rosters
  • Credentials encrypted at rest with a Fernet key (ENCRYPTION_KEY) — never stored or logged in plaintext
4 · Setup

Before the workshop (one-time)

Do this once per deployment

This is already done for the current live deployment — included here so a new proctor or a rebuild knows what "done" looks like. Check Settings → Configuration to confirm current values (secrets are redacted in the UI).

  1. Cognito configured
    User pool, domain, client ID/secret, region all set in .env. Confirm on Settings that cognito_domain/cognito_client_id are non-empty.
  2. Encryption key set
    ENCRYPTION_KEY — a 32-byte Fernet key. Without this, credentials can't be stored at all. Generate with python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())" — never reuse across environments.
  3. Proctor emails listed
    PROCTOR_EMAILS (comma-separated) — anyone on this list plus the permanent super admin gets access to Students/Classes/Progress/Settings/this guide. Manage via Students → Proctors in the UI, no manual .env editing needed day-to-day.
  4. Super admin's own ThousandEyes token saved
    On the super admin's own Credentials page, save a ThousandEyes token that belongs to the required training org (see §8). This is what drives auto-provisioning for every student — there is deliberately no separate service-account token.
  5. Shared Meraki key set (optional but recommended)
    MERAKI_SHARED_API_KEY / MERAKI_SHARED_ORG_ID in .env — gives every student working Meraki access with zero setup. Students can still override with their own key (see §9).
  6. Galileo configured (optional)
    GALILEO_API_KEY/GALILEO_PROJECT/GALILEO_LOG_STREAM — if unset, chat still works, just without observability. Dashboard link surfaces automatically in the admin nav once set.
  7. Sanity-check the lab guide
    Open /guide yourself and skim the ThousandEyes and Meraki lab prompts against the current demo org's actual data — placeholders like [network] need real names from the org that's connected today.
5 · Run-of-show

Day-of run-of-show

  1. Schedule the class (5 min before doors open)
    Go to Classes → Schedule a New Class → name, date, location. This generates a unique join link + QR code.
  2. Project the QR code
    Click the class row to open its QR modal, project/display it. Students scan it on their own device — no app install, just a browser.
  3. Students self-register
    They fill in name, company, email → Cognito account created instantly, temp password emailed. If ThousandEyes auto-provisioning is healthy, their dedicated Account Group is created in the background at the same moment (a few hundred ms slower, non-blocking).
  4. Watch the roster fill in
    The class's Roster modal on the Classes page shows everyone who's joined so far — useful for a headcount before you start talking.
  5. Kick off
    Point students at /guide (linked from the header once they're logged in) and have them work through Credentials → Verify connection → Labs, in order.
  6. Monitor live
    Keep Progress open on a second screen — sorted so students with the least progress float to the top, so you always see who needs help first.
  7. Unblock stuck students
    Most issues are one of: wrong/expired token, org mismatch, or a placeholder prompt sent verbatim. See §12 for the fast diagnosis for each.
💡
Keep this Proctor Guide open in one tab and Progress in another — you rarely need anything else during the live session.
6 · Rosters

Managing students & classes

👥 Students page

  • Add one student manually, or bulk-import a CSV/Excel roster
  • See every current student, their connection status per service
  • Add/remove proctors (the super admin is permanent and can't be removed)
  • "Reset Students" — for wiping a stale roster between unrelated cohorts

🏫 Classes page

  • Schedule/delete classes, each with its own QR/join link and roster
  • Disable class — soft-disables login for every enrolled student. Reversible; nothing is deleted.
  • Delete ThousandEyes Account Groups — separate, explicit, destructive action. Tears down every enrolled student's dedicated TE Account Group + user. Confirmed with a warning dialog; cannot be undone.
  • Deleting a class record itself does not touch student logins, credentials, or TE resources — do the disable/cleanup actions first if that's what you actually want.
⚠️
The two class-management actions that matter for "end of workshop" are separate on purpose: Disable (safe, reversible, just blocks login) vs. Delete TE Account Groups (irreversible, deletes real ThousandEyes resources). Don't run the second one until you're sure the workshop is fully over and no one needs their data.
7 · Monitoring

Monitoring live progress

The Progress dashboard merges Cognito's full user list with activity signals recorded server-side on every chat turn, so it shows:

ColumnWhat it means
TE / Meraki / Splunk connectedWhether that student has a working credential for each service right now
Labs completedWhich lab checkpoints they've hit, out of the full curriculum
% completeBased only on the required checkpoints — optional/bonus labs don't count against anyone
Chat message countTotal turns sent — a very low count with a connected credential usually means "stuck, not lost"
Last activeTimestamp of their most recent chat message

Students who haven't logged in yet still appear (pulled straight from Cognito) with zero progress, so no-shows are obvious at a glance. The list is sorted least progress first so the students who most need help are always at the top.

ℹ️
If Galileo is configured, the Metrics Dashboard link in the admin nav opens a separate, deeper view — tool selection quality, error rates, instruction adherence, etc. — useful after the session for retros, not usually needed live.
8 · ThousandEyes

ThousandEyes auto-provisioning

When a student self-registers, the app tries to give them their own dedicated ThousandEyes Account Group (named {{ '{name} ({email})' }}) plus a scoped user — so every student has real, isolated ThousandEyes access without a proctor doing anything by hand.

  1. Driven by the super admin's own token
    There is deliberately no separate service-account token in .env. Auto-provisioning always uses whatever ThousandEyes token the super admin ({{ super_admin_email }}) has saved on their own Credentials page — the same token they'd use to chat.
  2. Hard-locked to one organization
    Every provisioning/cleanup call is checked against a single required org name, currently "{{ required_org_name }}", hard-coded in thousandeyes_admin.py. If the super admin's token doesn't have an account group in that exact org, the app refuses to provision anything — it will never silently create resources in the wrong ThousandEyes organization.
  3. Non-blocking
    If the super admin hasn't saved a token, or it's for the wrong org, TE provisioning is simply skipped — the student's Cognito login still works fine, they'd just need their own ThousandEyes credential pasted in manually on the Credentials page.
⚠️
If TE provisioning stops working mid-workshop, the most common cause is the super admin's saved ThousandEyes token expiring. Re-save a fresh token on the super admin's own Credentials page — no restart needed, the next student join will pick it up.
9 · Meraki

Meraki shared credential

Unlike ThousandEyes, Meraki does not auto-provision a dedicated org per student. Instead, one shared class-wide API key + Org ID is configured server-side (MERAKI_SHARED_API_KEY / MERAKI_SHARED_ORG_ID in .env — never in source control) and used as a fallback:

  • Every student automatically has working Meraki access from the moment they log in — nothing to paste.
  • A student's own saved Meraki credential (if they add one on the Credentials page) always takes priority over the shared default.
  • If a student later deletes their personal credential, they automatically fall back to the shared default again — the fallback re-engages, it doesn't need re-enabling.
ℹ️
The Credentials page shows a note to students when the shared key is the one actually in effect for them, so there's no confusion about whose Meraki org they're looking at.
10 · Operations

System ops (restart, logs, deploy)

All under Settings, proctor-only:

Status tab

Live CPU/memory and whether the flask-app systemd service is active, plus a one-click Restart Flask App button (needed after changing .env values like proctor emails or the encryption key).

Logs tab

Tails journalctl -u flask-app with filters by user email, free text, log level, or a time window — the fastest way to see exactly why one student's request failed.

Deployment tab

Pull Latest Code runs git pull origin main in the app directory and restarts Flask automatically. Use this after merging any guide/app change during the workshop.

Configuration tab

View (redacted) and edit core .env values — Cognito settings, proctor emails, encryption key. Saving requires a restart to take effect (the Status tab button, or Deployment's pull, both restart it).

⚠️
If a git pull or any root-run command touches .git/objects as a different OS user, you may hit a "dubious ownership" error on the next manual git command over SSM. Fix with sudo chown -R ubuntu:ubuntu .git then run git as sudo -u ubuntu — cosmetic, doesn't affect the running app.
11 · Wind-down

After the workshop

  1. Disable the class
    Classes → find the class → Disable. Soft-disables every enrolled student's Cognito login. Fully reversible — nothing else is touched, so this is always safe to do immediately once the session ends.
  2. Decide on ThousandEyes cleanup
    Only if you're sure no one needs their data anymore: Classes → Delete ThousandEyes Account Groups. This is destructive and irreversible — it deletes the dedicated Account Group + user for every student in that class. There's a confirmation dialog; read it.
  3. Leave students' credentials/progress alone
    There's no need to delete student records after a session — they're harmless at rest (encrypted), and keeping them lets you pull retro numbers from Progress/Galileo later.
  4. Optional retro
    If Galileo is configured, the Metrics Dashboard link (Settings/Students/Progress nav) is the best place to review tool-selection quality and error rates across the whole cohort after the fact.

13 · Security

Security notes

  • No credential (API key, token, secret) is ever stored in source code — only in encrypted DynamoDB fields (per-student) or the server's gitignored .env (shared defaults like the Meraki fallback key).
  • Credentials are encrypted at rest with a Fernet key and are never returned to the browser in plaintext, including on the proctor's own Credentials page.
  • Proctor access is an explicit allow-list (PROCTOR_EMAILS + one permanent super admin) — being logged in is not enough on its own.
  • ThousandEyes auto-provisioning is hard-locked in code to one named training organization — it will refuse to run rather than risk touching the wrong org, even if the super admin's token happens to have access to others.
  • Student logins can be soft-disabled (reversible) independently of any destructive ThousandEyes cleanup (irreversible) — these are always separate, explicitly confirmed actions.
